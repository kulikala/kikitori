# 文書の書き方

kikitori の文書（README・CHANGELOG・`docs/` の文書・`skills/kikitori/SKILL.md`）を書くときの方針です。
公開する文書は、kikitori を初めて知った人が、それだけを読んで使い始められるように書きます。

## 読み手と、それぞれが知りたいこと

- README の読み手は利用者です。何ができるか、自分の PC で何が動くか、どう入れて、どう更新・取り外すかを知りたがっています。
- `docs/DESIGN.md` の読み手は kikitori を直す開発者です。なぜその作りにしたかを知りたがっています。
- `docs/RELEASING.md` の読み手は版を出す人です。何をどの順に打てばよいかを知りたがっています。
- SKILL.md の読み手は LLM のエージェントです。利用者に代わって kikitori を正しく使うための手順と注意を求めています。
- CHANGELOG の読み手は版を上げる利用者です。自分の使い方に響く変更を知りたがっています。

## 意図と仕組みを書き、実装には踏み込まない

ツールが何のためにあり、どういう考えで組み立てられているかは、利用者の判断を助けるので書きます。
関数名・閾値・依存する部品の名前・処理の細かな順序は、コードが正しい置き場所です。文書に写すと、コードが変わったときに文書だけが古くなります。
開発者にどうしても伝えるべき設計の理由は、`docs/DESIGN.md` にまとめます。

## 今の kikitori そのものを書く

文書には作業の経緯や報告（何を試したか、どう直したか、誰が確かめたか）を書きません。
対応状況や精度は、確かめた範囲と未確認の範囲を、今の事実として書きます。変更の経緯は CHANGELOG と版管理の履歴が持ちます。

## 誰の PC でも成り立つことを書く

書いた人の PC や、試しに使った仮想マシンに固有の情報（フォルダのパス、メモリの量、OS の細かな版、その環境で測った所要時間）は書きません。
測った値を載せるときは、利用者が自分の環境に置き換えて読めるように、何で測ったかを短く添えます。

## 利用者を縛りすぎない

利用者に求めるのは、kikitori を動かすのに本当に要ることだけにします。
勧めたい使い方は勧めとして書き、決まりのように書きません。

## 細かくしすぎない

利用者が求めているのは、概要と意図です。1 つの節では、伝えたいことの要点をまず書き、例外や補足は要るものだけを後に添えます。
迷ったら、それを読まなかった利用者が困るかで決めます。困らないなら書きません。
