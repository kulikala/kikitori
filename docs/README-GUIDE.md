# README の書き方

kikitori は日本語の会議の録音を話者ごとに分けて文字にするコマンドラインツールです。文字起こしのほかに、誤りを直す補正（`kikitori refine`）を持ちます。この文書は kikitori の README と、README から分けた利用者向けの文書（`docs/INSTALL.md`・`docs/USAGE.md`・`docs/DISCLOSURES.md`・`docs/MODELS.md`）を書くときに目指すことと、変更を書いてから見直すまでの進め方をまとめたものです。以下、これらをまとめて利用者向けの文書と呼びます。

README は kikitori を試すか決めるとき、インストールするとき、困ったときに読まれます。README・CHANGELOG・`docs/` の文書に共通する方針は [WRITING.md](WRITING.md) にあります。読み手ごとに文書を分けること、実装の細部（関数名や閾値）を写さないこと、今の kikitori を書き経緯を書かないこと、書いた人の PC に固有の値を載せないことです。この文書はそれを利用者向けの文書に当てはめたもので、README を直す前に WRITING.md も読んでください。2 つが食い違って見えるときは、利用者向けの文書についてはこの文書に従います。決まりの一覧ではないので、この文書に書いていない場面では、README を読む人の助けになるほうを選んでください。

## 読む人

- **試すか決める人**は GitHub で README を開き、数十秒で決めます。日本語の会議に使えるか、自分の PC で動くか、録音が外へ出ないかを知りたがっています。
- **インストールする人**は手順の前に、必要なもの・ディスクの容量・管理者権限の要否を知りたがっています。
- **困っている人**は、終了コードや、ターミナルに出た文言を手がかりに来ます。
- **用心深い人**は何をどこから取得し、どこに何を書き、何が PC の外へ出て、どう消せるかを、インストールする前に確かめたがっています。
- **エージェントに任せる人**は、Claude Code や Codex に kikitori を使わせるために何を用意すればよいかを探しています。
- **開発者**は設計や手順の文書への入口を 1 つ探しています。

## README と、分けた文書の受け持ち

README は、試すか決める人が数十秒で読み切れる長さにとどめ、何をするか、機能区分（文字起こしと補正）、特長、向いている用途（向かない用途を含む）、対応環境、必要なディスク容量、別途必要なソフトウェア、OS ごとのインストールのコマンド、機能区分ごとの使い方、エージェント・スキル、精度の要点、開発者ガイド、ライセンスを、この順の章で書きます。細部は README に盛らず、次の文書に置いて README からリンクします。README の概要は読み手を詳しい文書へ導くための短い要約です。条件や値の正は詳しい文書の側に置き、README の要約はそれに合わせます。

| 文書 | 受け持つこと |
|---|---|
| `docs/INSTALL.md` | 対応環境と NVIDIA の GPU、必要なディスク容量、別途必要なソフトウェア、インストール、インストールの環境変数、ターミナルの無い環境、更新、削除、0.2.x からの移行 |
| `docs/USAGE.md` | 文字起こしのオプションと出力形式、辞書、補正の仕組みと選び方、外部の LLM、エージェントから使う仕組み、終了コード、困ったとき |
| `docs/DISCLOSURES.md` | 通信する先、起動するプログラム、書き込むもの |
| `docs/MODELS.md` | 精度と速さ、仕組み、モデルとライセンス |

表に無い利用者向けの事実は、利用者がその事実を探す場面に近い文書に置きます。決まらなければ `docs/USAGE.md` に置きます。開発者向けのことは `docs/DESIGN.md`（設計）・`docs/ENGINES.md`（認識エンジンの足し方）・`docs/RELEASING.md`（リリースの手順）に、版ごとの変更は CHANGELOG に書き、README の「開発者ガイド」の章の表からリンクします。

## 目指すこと

**何が手に入るかを、確かめられる言葉で言う。** README の冒頭では、kikitori が何をするか、誰に向くか、ほかの道具と何が違うかを書き、出力の例を見せます。読み手が自分で確かめられることだけを書き、売り込む言葉も、不安をあおる言葉も使いません。向かない使い方（日本語以外の録音、句読点が必要な本文など）も、インストールする前に分かる位置に書きます。

**初めて読む人に向けて書く。** 読み手はコードも、これまでの版も、作ったときのやり取りも知りません。補正の説明に出る A・B・K のような記号（A は直す対象の文字起こしの本文、B と K は根拠にする 2 つの音声認識）や、「区間」（補正が直す単位にする発言のひとまとまり）のように kikitori で決めた語は、それぞれの文書の中で初めて出る所で 1 度だけ意味を言い、あとは意味を言わずに使います。利用者向けの文書はどれも単独で読まれるためです。README の冒頭のように、まだ意味を言っていない所では、記号に頼りません。

**CLI と同じ言葉で書く。** 利用者は README の語を `kikitori doctor` の出力、`--help`、ターミナルに出る文言と見比べます。README の書き手は、README の語を CLI が出す語に合わせ、CLI の側に無い呼び名を作りません。CLI の語が初めて読む人に分かりにくいときも、語は替えずに、初めて出る所で意味を添えます。CLI の中で語が揺れているときは、利用者がいちばんよく見る `kikitori doctor` の出力に合わせ、そこに無い語は `kikitori refine` が stderr に出す説明に合わせます。

**外部のソフトウェアと容量は、それぞれの章に書く。** Ollama・ffmpeg のように利用者が各自でインストールするソフトウェアは「別途必要なソフトウェア」の章に、ソフトウェア・バージョン・要否・説明の表で書きます。要否が任意なら、どの場面で必要かを添えます。ダウンロードするモデルの容量は「必要なディスク容量」の章に、機能区分・ダウンロードするモデル・用途・容量の表で書きます。インストールの章は OS ごとの節に分け、コマンドだけを書きます。インストールスクリプトの働き、対応環境、容量、使い方は書きません。ほかの節でも、利用者がソフトウェアを自分でインストールすることを地の文で述べず、その章へリンクします。

**1 つのことは、読み手が探す 1 か所に書く。** 確認が出る場面、終了コードの一覧のように、何度も出したくなる事実は、置き場を 1 つ決め、ほかの所からはリンクで指します。長い説明が必要な細部は、`--help` や `kikitori doctor` のように、利用者が自分の PC で確かめられる場所に任せることもできます。

**信頼に関わる所は全部書く。** 用心深い人のために、kikitori が通信する先と取得するもの、起動するプログラム、書き込むファイルとその場所、録音の文字が PC の外へ出る場面を、`docs/DISCLOSURES.md` に漏れなく書きます。この文書では短さより完全さを優先します。インストールと削除の説明には、手順に必要な分（置き場や容量）だけを書き、全体は `docs/DISCLOSURES.md` へリンクで任せます。両方に出る値は`docs/DISCLOSURES.md` を正として、ほかを合わせます。

**対応環境は対応表で書く。** 利用者が知りたいのは、自分の PC で何が動くかです。対応環境はOS ごとに、機能（文字起こし・補正）を CPU と GPU のどちらで動かすかを表にします。どこまで試したかのような作業の記録は、利用者向けの文書に書きません。速さや精度の値には、何を何で測ったかを短く添えます。新しく載せる値は誰でも手に入る公開のデータで測ったものにします。

**今の版を書く。** README は最新のリリースを説明します。次のリリースで変わる動作は、その変更と同じコミットで書き直します。日付、試した順、計画、変更の経緯は CHANGELOG と版管理の履歴が持ちます。kikitori には以前 Python で書いた版（0.2.x）があります。0.2.x は保守していないので、0.2.x を使う案内は書きません。0.2.x からの移行だけを、今の利用者に必要な手順として書きます。

**ほかの場所が頼っているものを残す。** CHANGELOG は README の「インストール」の見出しにリンクします。見出しの名前を変えるときは、`git grep` でリンクと案内を探し、切れないようにします。

## 日本語の書き方

利用者向けの文書は日本語だけで書きます。和文と、欧文の語や数字の間には半角スペースを入れます。CLI の日本語の出力も同じ書き方です。

## 変更を書いて見直す

手順 2〜4 は生成 AI のエージェント（Claude Code・Codex）で使う推敲のスキルを使います。remove-meta-narrative と review-for-readers は wakariyasu に、yomiyasu は [yomiyasu](https://github.com/nanaism/yomiyasu) に入っています。スキルを使えないときは、手順 2〜4 に書いた観点で、人が読んで直します。

1. 書く。コマンド、オプション、環境変数、ファイルの置き場、容量、終了コードを、コードと、`cargo build --release` で作った kikitori の `--help` の出力で確かめます。
2. 文書が自分自身や作った経緯を語る文（「本節では」「〜に改めました」など）を探し、対象そのものを語る文に直します（remove-meta-narrative）。
3. 経緯を知らない読み手に、README と、変えた利用者向けの文書だけを、README の頭から順に読んでもらいます（review-for-readers）。読み手は、変更の経緯を渡していない別の人か、会話の経緯を渡していない別のエージェントです。読み手は上の「読む人」を 1 人ずつ演じ、それだけでは意味が通らない所、同じ文書の中や詳しい文書どうしで 2 度書いてある所、README の要約と詳しい文書の食い違い、指す先が分からない語、根拠の無い主張を挙げます。直したら、別の読み手に読み直してもらい、読み手が誤解したり行き詰まったりする所が挙がらなくなるまで繰り返します。目安は 2〜3 回です。
4. yomiyasu で推敲します。不自然な比喩、主語と述語のかみ合わない文、同じ形の文末の続きを直し、意味と条件は変えません。yomiyasu には文書の種類として article（技術記事・README）を渡します。和欧の間の半角スペースはyomiyasu の指示より上の「日本語の書き方」を優先します。
5. `python scripts/check_public.py` を通します。顧客名や手元のパスのように、公開してはいけない語が入っていないかを確かめる検査です。語の一覧はリポジトリの外に置き、公開するメンテナが持っています。一覧が無い PC では、検査は一覧が無いと出して止まります。そのときは、検査を通していないことを変更の説明（PR の本文など）に書き、メンテナが公開の前に通します。語が見つかったら、出た箇所を直して、通るまで実行し直します。

誤字の直しや、コードに合わせた値の更新のように、文の意味と構成を変えない変更は、手順 1 と 5 だけで足ります。文を書き足す・言い換える変更は、手順 1 から 5 まで通します。
