# 設計の考え方

kikitori を直す開発者向けに、作りの理由をまとめます。使い方は README、細かな値はコードにあります。

## Rust の 1 本の実行ファイルにする

利用者の PC に Python と、その部品の導入を求めないために、Rust の 1 本の実行ファイルとして配ります。導入は 1 行で、管理者権限は要りません。Release から自分の環境の実行ファイルを取り、チェックサムを確かめて置きます。

対応は macOS（Apple Silicon）、Linux（x86_64・arm64）、Windows（x64・arm64）です。GPU が無い PC でも、Mac で GPU を使わせない指定でも、同じ使い方で全機能が動くことを基準にしています。NVIDIA の GPU 向けには、CUDA 版を別の資産として配ります。CUDA を実行時に読み込む形なので、GPU の無い機械でも起動し、CPU に戻ります。

リポジトリは Cargo のワークスペースで、役割ごとにクレートを分けます。

| クレート | 役割 |
|---|---|
| `kikitori-core` | 型、エンジンの口、レジストリ、パイプライン、出力形式。重い依存を持たない |
| `kikitori-audio` | 音声の読み込みと 16 kHz モノラルへの変換 |
| `kikitori-sherpa`・`kikitori-reazon` | ReazonSpeech の認識、Silero VAD、話者分離 |
| `kikitori-qwen3asr`・`kikitori-whisper` | 補正の B（Qwen3-ASR）と K（kana-whisper） |
| `kikitori-dict` | 読みの一致による置換（`--dict`）と、用語集の読み |
| `kikitori-refine` | 補正の経路の選択、Ollama、外部 LLM、長さの規則 |
| `kikitori-fetch` | モデルの取得とキャッシュ |
| `kikitori` | コマンドライン（バイナリ名 `kikitori`） |

ライブラリとして使う人は、`kikitori-core` と使うエンジンのクレートだけに依存します。

## 文字起こしと補正を分ける

`kikitori transcribe` は、録音を話者つきの文字に起こすところまでを受け持ち、LLM を使いません。同じ録音・同じモデル・同じ計算機からは同じ結果が出るので、結果を比べたり、ほかの道具に渡したりしやすくなります。

誤りを直す補正は、サブコマンド `kikitori refine` が受け持ちます。補正は大きなモデルを要し、動く環境も限られます。分けておくと、補正の環境を入れなくても文字起こしだけは使えます。

どちらも、既定では PC の外へ何も送りません。モデルは認証なしで取得できる配布物だけを使います。

## 文字起こしの流れ

1. 音声を 16 kHz モノラルにそろえる。主な形式は ffmpeg なしで読み、読めない形式（Opus など）だけ、ffmpeg があれば任せる。無ければ案内を出して終わる。
2. 発話のある区間を見つける。
3. 話者の区間を求める。
4. 発話の区間を、話者が交代する位置でだけ切る。発言を途中で切らないためです。
5. 区間ごとに認識する。長さの近い区間をまとめて認識し、長い録音でもメモリが増えすぎないようにしています。
6. 辞書があれば、読みの一致で表記を置き換える。

出力の形式は、配列だけの `json` と、版を持つ `json-v1` を両方残します。既存のスクリプトの形を壊さず、機械で読む側には版つきの形を勧めるためです。

## 計算機を選ぶ

文字起こしの本体（ReazonSpeech）は CPU で動かします。GPU より速いとは限らず、CPU で十分な速さが出るためです。補正の B と K は、`--device auto` が Metal → CUDA → CPU の順に、ビルドに入っている候補を試し、初期化の失敗や panic を失敗として扱って次へ進みます。GPU を指定したのに黙って CPU で動く状態は、GPU として扱いません。選んだ計算機と理由は、診断（`-v`、`--log-format json`、`doctor`）に出ます。

数値精度は計算機とモデルごとに決めます。Metal では B が f16、K が f32 です。K を f16 にすると、元の実装と本文が一致しない録音が出るためです。CPU は f32 です。

## メモリは始める前に見る

B と K の読み込みには CPU の fp32 で約 9.7GB、Metal と fp16 で約 5.6GB を見積もります。補正は B で全区間を起こして捨ててから K を読み込み、同時には載せません。`doctor` が空きメモリと見込みを出し、足りないときは始める前に終了コード 11 で止め、`--dtype fp16` か `--force` を案内します（CUDA では見積もりません）。

## 認識エンジンを差し替えられる

認識（`AsrEngine`）、発話区間（`Vad`）、話者分離（`Diarizer`）は別の口で、コアはモデルの種類を知りません。エンジンは各クレートが `specs()` で登録を出し、CLI が Cargo の feature で束ねます。自動登録の仕組みは使いません。静的リンクでもテストが同じ結果になるようにするためです。

選び方は名前（`--asr`、`--diarizer`、補正は `--engine-b`・`--engine-k`）か、Hugging Face のリポジトリ名（`hf:<名前>`）です。足し方は [ENGINES.md](ENGINES.md) にあります。

重みは配布元のファイルをそのまま読みます。変換や量子化をして配ることも、キャッシュに派生物を書くこともしません。

## モデルの取得

kikitori のモデルの置き場は `~/.cache/kikitori/models`（`KIKITORI_MODELS`）、Hugging Face のモデルは Hugging Face 標準のキャッシュの形です。Hugging Face へは REST で直接つなぎ、リビジョンはコミットで固定します。ファイルごとにサイズと SHA-256 を照合し、途中で切れたら続きから取ります。

先に別の方法で取得してあるモデルは取り直しません。ファイルの内容が同じなら、既存のキャッシュを使います。Python 版 0.2.x が取得したモデルをそのまま使えるのは、このためです。

## 補正の直し方を環境で選ぶ

補正は、文字起こしの本文（A）を、同じ区間を別の 2 つの認識で文字にした結果（B と K）を根拠に直します。直し方は使える道具の多い順に選びます。

1. 外部の LLM を指定されたら、それに任せる。
2. 大きなモデルが Ollama にあれば、区間ごとに A・B・K を突き合わせて書かせる。
3. 小さな判定用のモデルがあり、用語集があれば、用語集の語に置き換えるかを選ばせる。
4. どれも無ければ、B が A より十分に長い区間だけ B を採る。

どの段でも結果は出ます。Ollama が止まっていても補正は失敗せず、下の段に下がって、その旨を出します。普段の補正では Ollama を起動しません。起動や導入は `kikitori refine --setup` の仕事です。

機器ごとに使う Ollama のモデルは 1 つの表にまとめてあります。`--setup` が取得するモデルと、補正のときに選ぶモデルが、同じ表と同じ式で決まるので、取得したのに使われないモデルが出ません。モデルを使うのは、モデルを置くメモリが「モデルの大きさ＋8GB」以上のときだけです。Apple Silicon では MLX 版を、それ以外では GGUF 版を選びます。

## 生成 AI から使う前提の CLI

エージェントが利用者に代わって打つことを前提に、次を守ります。

- 結果は stdout、進み具合と警告は stderr。`--log-format json` で stderr を 1 行 1 件の JSON にできる。外部のライブラリが stderr に書く行も、この形に包む。
- 終了コードは失敗の種類ごとに決め、失敗の表示に次に打つコマンド（`hint`）を入れる。
- 対話が要る所を作らない。大きな取得と削除は `--dry-run` で中身と容量を出し、`--yes` で確認を省く。端末が無いときは確認を待たずに終了コード 6 で終わる。
- JSON の形は `schema` サブコマンドで出せ、テストで実際の出力と照合する。
- 同梱の SKILL.md（`crates/kikitori/skill/SKILL.md`）を `skill install` でエージェントの置き場に書く。リポジトリ直下の `skills/kikitori/SKILL.md` は同じ内容のコピーで、テストで同一を検査する。

## 導入・更新・削除

導入は、取得した実行ファイルを一時の場所で `--version` まで確かめてから置きます。Python 版が同じ名前で入っていれば、先に外します。更新は、今の実行ファイルを退避してから置き、新しい版が起動しなければ退避を戻します。

削除のために、kikitori が実際に置いたもの（実行ファイル、PATH の行、モデルの置き場、スキル、取得した Ollama のモデルなど）を受け取り記録に 1 行ずつ書きます。`uninstall` は記録に載っているものと既定の置き場だけを一覧にして消します。利用者が先に入れていたもの（Ollama 本体、自分で取得したモデル）は、記録に無いので消しません。

導入スクリプトは GitHub の Release に載せ、その Release の実行ファイルを入れます。Windows の `install.ps1` は、英字だけで書いた入口です。Windows PowerShell 5.1 の `irm` は、日本語を含むスクリプトを UTF-8 として読まないので、入口が本体の `install-windows.ps1` をバイト列で取得し、UTF-8 として読んで実行します。

## 公開するもの

公開するのは `main` の履歴だけです。録音に出てくる顧客名などが紛れ込まないよう、公開前に禁止語の一覧で履歴と配布物を調べます（手順は [RELEASING.md](RELEASING.md)）。一覧はそれ自体が公開できない語なので、リポジトリの外に置きます。
