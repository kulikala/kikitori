# 設計の考え方

kikitori を直す開発者向けに、作りの理由をまとめます。使い方は README、細かな値はコードにあります。

## 2 つのコマンドに分ける

`kikitori` は、録音を話者つきの文字に起こすところまでを受け持ち、LLM を使いません。同じ録音・同じモデル・同じ計算機からは同じ結果が出るので、結果を比べたり、ほかの道具に渡したりしやすくなります。

誤りを直す補正は、別のコマンド `kikitori-refine` が受け持ちます。補正は torch や Ollama のような大きな部品を要し、動く環境も限られます。分けておくと、補正が動かない環境でも文字起こしだけは入れられます。

どちらも、既定では PC の外へ何も送りません。モデルは認証なしで取得できる配布物だけを使います。

## 文字起こしの流れ

1. 音声を 16 kHz モノラルにそろえる。
2. 発話のある区間を見つける。
3. 話者の区間を求める。
4. 発話の区間を、話者が交代する位置でだけ切る。発言を途中で切らないためです。
5. 区間ごとに認識する。長さの近い区間をまとめて認識し、長い録音でもメモリが増えすぎないようにしています。
6. 辞書があれば、読みの一致で表記を置き換える。

## 計算機を測って選ぶ

GPU があっても、CPU より速いとは限りません（Apple Silicon の CoreML は CPU と同等かやや遅い）。そこで `--device auto` は、実際の音声の先頭で CPU と GPU を試し、GPU がはっきり速いときだけ GPU を使います。GPU を指定したのに黙って CPU で動く状態は、GPU として扱いません。

## 補正の直し方を環境で選ぶ

補正は、`kikitori` の本文（A）を、同じ区間を別の 2 つの認識で文字にした結果（B と K）を根拠に直します。直し方は使える道具の多い順に選びます。

1. 外部の LLM を指定されたら、それに任せる。
2. 大きなモデルが Ollama にあれば、区間ごとに A・B・K を突き合わせて書かせる。
3. 小さな判定用のモデルがあり、用語集があれば、用語集の語に置き換えるかを選ばせる。
4. どれも無ければ、B が A より十分に長い区間だけ B を採る。

どの段でも結果は出ます。Ollama が止まっていても補正は失敗せず、下の段に下がって、その旨を出します。普段の補正では Ollama を起動しません。起動や導入は `kikitori-refine --setup` の仕事です。

## モデルを 1 つの表で決める

機器ごとに使う Ollama のモデルは、1 つの表（`src/kikitori/refine/catalog.py`）にまとめてあります。`--setup` が取得するモデルと、補正のときに選ぶモデルが、同じ表と同じ式で決まるので、取得したのに使われないモデルが出ません。

モデルを使うのは、モデルを置くメモリが「モデルの大きさ＋8GB」以上のときだけです。Apple Silicon では MLX 版を、それ以外では GGUF 版を選びます。

## 導入は 1 行で、Release から

導入スクリプトは GitHub の Release に載せ、その Release の wheel を入れます。リポジトリの中のスクリプトには wheel の URL の代わりに置き換え用の印があり、Release を作るときに URL を書き込みます。

Windows の `install.ps1` は、英字だけで書いた入口です。Windows PowerShell 5.1 の `irm` は、日本語を含むスクリプトを UTF-8 として読まないので、入口が本体の `install-windows.ps1` をバイト列で取得し、UTF-8 として読んで実行します。

部品の配布物が無い環境（ARM の Windows など）では、依存の条件でその部品を外し、使えない機能は案内を出して終えます。導入そのものは止めません。

## 公開するもの

公開するのは `main` の履歴だけです。録音に出てくる顧客名などが紛れ込まないよう、公開前に禁止語の一覧で履歴と配布物を調べます（[RELEASING.md](RELEASING.md) の「公開前の検査」）。一覧はそれ自体が公開できない語なので、リポジトリの外に置きます。
