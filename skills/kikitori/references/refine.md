# 補正（kikitori refine）

`kikitori refine` は、音声を受け取って文字起こしからやり直し、区間（文字起こしが区切った発言のひとまとまり。json-v1 の `segments` の 1 要素）ごとに本文を直します。直す対象の本文を A、根拠にする 2 つの音声認識を B（Qwen3-ASR。漢字かな交じり）と K（kana-whisper。音をカタカナで書く）と呼びます。B は A が落とした発話を拾う一方、話されていない文を作ることがあります。

## 用語集

`--glossary` で渡す用語集は、1 行 1 語の `表記<TAB>補足`（補足は読みや説明。省ける）です。会議の資料などにある社名・地名・製品名を書くと、LLM がその表記に直します。`--dict` の辞書（`表記<TAB>読み`）も同じ形なので、そのまま用語集に使えます。逆向きに、用語集を `--dict` に使えるのは、2 列目がどの行も読みのときだけです。2 列目が説明だと、読みとして照合されて誤った置き換えが起きるためです。何を書くかは利用者が知っていることなので、依頼から読めなければ確かめます。

## 直し方

`kikitori refine` は次の上から順に、最初に当てはまる直し方を選びます。選んだ直し方と理由は stderr（`--log-format json` では `info`・`warning`）に出て、`--plan` で前もって見られます。

| 当てはまる状況 | 直し方 |
|---|---|
| B・K のモデルが無く、取得しない | 文字起こしの本文のまま |
| `--external` を付けた | 外部の LLM が A・B・K と用語集を見て直す |
| Ollama に突き合わせ用の大きなモデルがある | 区間ごとに、そのモデルが A・B・K を突き合わせて本文を書く |
| Ollama に小さなモデル（tev1、0.8GB）があり、`--glossary` を付けた | 長さの規則のあと、用語集の語に置き換えるかを tev1 が選ぶ |
| どれにも当たらない（Ollama が応答しないなど） | 長さの規則。B の文字数が A の 1.6 倍＋3 文字を超える区間だけ B を採り、A が落とした発話を補う |

同じ会議録音 1 本で測った文字誤り率は、本文のままが 28.4%、外部の LLM（Claude Haiku）が約 20%、大きなモデルの突き合わせが約 22%、tev1 と長さの規則が約 25% でした。ほかの録音で同じ差が出るとは限りません。

- 大きなモデル（Apple Silicon は `qwen3.8:27b-mlx`、NVIDIA は `qwen3.8:27b-q4_K_M`、どちらも 18GB）は、モデルを載せるメモリが 26GB 以上ある PC でだけ使われます。載せるメモリは、Apple Silicon では本体のメモリ、NVIDIA では最も大きい GPU 1 枚のメモリです。CPU だけの PC では使われません。
- 直し方が利用者の望みに足りないときは、利用者に Ollama を入れて起動してもらってから `kikitori refine --setup` でモデルを取得するか（取得なので了承が要る）、利用者が外部の LLM を使うと言っていれば `--external` に進めます。
- `kikitori refine` は Ollama を起動しません。Ollama が止まっていれば長さの規則に切り替え、終了コード 0 で終わります。kikitori は Ollama を入れも起動もしないので、Ollama の起動は利用者に頼みます。
- B・K が無いと取得の確認が出て、あなたの実行では終了コード 6 で止まります。了承を得て `--yes` を付けるか、先に `kikitori models pull --refine --yes` で取得します。
- 手元の PC で動かす LLM は Ollama だけに対応しています。利用者が Ollama 以外の手元の LLM（LM Studio など）を使いたいと言ったら、kikitori からはつなげないと伝えます。
- Ollama は 0.40.0 以上が要ります。古いと `kikitori refine --setup` は LLM のモデルを取得せず、更新の案内を出します。
- 大きなモデルの名前は `--merge-model <名前>`（環境変数 `KIKITORI_LLM`）で替えられます。

## あなたが直す（--external bundle）

本文と用語集が、あなたの動いている LLM のサービスへ渡ります。利用者がそれでよいと言っているときだけ行います。Ollama で直すより正確になる見込みです。

```bash
kikitori refine 会議.m4a --glossary 用語集.tsv --external bundle > プロンプト.json
```

1. `プロンプト.json` の `system` を指示として読み、`chunks` の各 `user` に応答します。応答は区間ごとに `[番号] 本文` の 1 行です。番号は `chunks[].ids` に従い（配列の添字ではありません）、行数と番号が `chunks[].ids` と一致することを確かめます。形は `kikitori schema bundle` で確かめられます。指示に書かれた規則に従い、要約・言い換え・敬語の整形はしません。
2. 応答を `chunks` の順につないでファイルに書き、`kikitori refine --apply プロンプト.json --reply 応答.txt --format json-v1` を実行します。応答の無い区間は元の本文のまま残り、stderr に警告が出ます。

`--external claude` を付けると、この 2 つの手順を `claude` コマンド（Claude Haiku）が行います。本文は Anthropic のサービスへ渡るので、利用者が外部の LLM を使うと言っているときだけ実行します。

`--save-evidence 根拠.json` を付けると、A・B・K の認識結果を保存します。次からは `--evidence 根拠.json` で認識を省き、直し方だけを替えて試せます。

## 時間とメモリ

- 補正は文字起こしより時間がかかります。B・K の分だけで、CPU では音声の長さの約 1.5 倍、Mac の Metal では約 0.15 倍でした。これに文字起こしの時間が加わります。コマンドの実行時間に上限がある環境では、先に見積もります。使う計算機は `kikitori doctor` の「使う計算機（既定）」の行で分かります。
- B・K を読み込む前に、要るメモリを見積もります。B を fp32 で動かすと約 9.7GB、fp16 では約 5.6GB です。Metal の既定は fp16 で、CPU でも `--dtype fp16` を付けられます。足りない見込みなら終了コード 11 で止まります。
