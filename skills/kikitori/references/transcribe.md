# 文字起こし

## 実行の例

```bash
kikitori transcribe 会議.m4a --num-speakers 4 --format json-v1 > 会議.json   # LLM や道具で読む
kikitori transcribe 会議.m4a --dict 辞書.tsv                                 # 辞書つき（テキスト）
kikitori transcribe 会議.m4a --format srt > 会議.srt                          # 字幕
kikitori transcribe 会議.m4a --model ja-en                                   # 日英が混ざる会議
```

## 音声

m4a・mp4・mp3・wav・flac・ogg は、そのまま読めます。Opus（Google Meet の webm など）は ffmpeg が要り、無ければ終了コード 4 で止まって、入れ方が `hint` に出ます。ffmpeg を入れるのは了承を得てからです。

文字起こしのモデルが無ければ、最初の実行で取得します（約 800MB）。あなたの実行では確認で終了コード 6 になるので、了承を得て、先に `kikitori --yes setup` で取得しておけます。

## 出力形式（--format）

| 形式 | 使うとき |
|---|---|
| `json-v1` | LLM や道具で読むとき。`schema_version` と `segments` を持つオブジェクト |
| `json`・`yaml` | 発言の配列が欲しい道具に渡すとき（0.2.x と同じ形）。yaml は json より短い |
| `txt`（既定） | 人が読むとき。1 行 1 発言の `[分:秒.小数] 話者N: 本文` |
| `srt`・`vtt` | 字幕の道具に渡すとき。時刻の行と本文の行が分かれていて、発言の対応を読み取りにくいので、LLM で読むときには向かない |

形の定義は `kikitori schema <名前>` で JSON Schema として出せます。名前は `transcript-v1`（json-v1）・`transcript`（json・yaml）・`bundle`・`doctor`・`engines` です。無音だけの録音は空の結果で終了コード 0 になります。

## 精度を上げる

- **人数。** `--num-speakers N` で渡します。指定の人数に分けられなかったときは、stderr に警告が出ます。
- **辞書（--dict）。** 利用者が書くファイルで、1 行 1 語、`表記<TAB>読み`（読みはひらがなでもカタカナでもよい）です。認識した語の読み（発音、合わなければ綴りの読み）が辞書の読みと一致したときに、表記へ置き換えます。読みが違う語は置き換わらないので、会議に出そうな語を多めに書けます。置き換えた発言の数は stderr に出ます。
  - 読みは形態素解析の辞書（unidic-lite。`--dict` のファイルとは別のもの）から引きます。無ければ取得の確認が出て、あなたの実行では終了コード 6 で止まるので、了承を得て `--yes` を付けます。
  - 辞書は認識のあとの置き換えなので、音そのものを聞き違えた誤り（「東京リージョン」が「東京水温」になるなど）は直りません。辞書で直らなかったとき（stderr が「0 区間を置き換えました」など）は、辞書の読みを誤認識に合わせて書き換えず、辞書では直らないことを利用者に伝え、補正を使うかを確かめます。誤認識に合わせた読みはほかの正しい語まで置き換えてしまうためです。
- **Zoom の参加者ごとの録音。** Zoom の「参加者ごとに個別のオーディオファイルを記録」の録音は、話者分離が要らず、いちばん正確です。ファイルごとに `--num-speakers 1` で起こします。話者番号はどれも `0` になるので、人物はファイル名から対応づけます。録音の開始時刻がそろっているかを利用者に確かめ、そろっているときだけ `start` の順に並べます。分からなければ、ファイルごとの結果をそのまま渡します。
- **英語の多い会議。** `--model ja-en` を試します。既定の `ja` は英語を認識しない代わりに、話されていない英語の語が紛れ込みにくい作りです。補正は日本語だけなので、補正と日英混在の両方が要るときは、`--model ja-en` の結果を渡し、補正できないことを利用者に伝えます。

## 時間の目安

67 分の会議を Apple Silicon の Mac の CPU で起こすと、約 280 秒でした（音声の長さの約 0.07 倍）。長い録音では、ffmpeg があれば `ffmpeg -t 300 -i 会議.m4a 先頭.m4a` で先頭の 5 分を切り出して試し、人数・辞書・出力形式の指定を確かめてから全体を起こせます。

## 精度

朗読の公開データ（FLEURS）では、文字誤り率が kikitori 5.9%、Whisper large-v3-turbo 5.2% で、Whisper のほうが正確です。放送の自然な発話（ReazonSpeech の評価用データ）では 7.1% 対 10.9% で kikitori が上回りますが、このデータは kikitori の認識モデルと同じ系統で、kikitori に有利です。会議の音声そのもので比べた値ではありません。
